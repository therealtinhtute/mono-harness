Workflow

The normal durable path from a rough idea to a persisted handoff, and the reduced modes for when the change is small enough not to need a ledger.

The durable path

Each stage runs a read-only zharness preflight check first. Durable modes require an initialized, readable database and current managed docs; reduced modes continue without them.

/brainstorm

explore options, lock requirements

→

/to-plan

phases, waves, tasks, checks

→

/work

execute, verify each task

→

/check

gates and review

→

/git

stage, commit, push, PR

→

/handoff

persist state, next action

Reduced modes

Use the smallest mode that matches the work. Reduced work writes no lifecycle rows — the git diff plus captured proof are its durable evidence.

Reduced modes

/brainstorm exploreresponse-only exploration.
/work simple <task>bounded change, no lifecycle rows.
/check boundedresponse-only gate for bounded work.
/watzupread-only resume and branch recap.

The journey

First run, initialize — zharness init creates the root harness.db, replays existing changesets, and scaffolds the managed docs. Then the durable path is a straight line: /brainstorm → /to-plan → /work → /check → /git → /handoff. At any point, /watzup reconstructs where things stand when a session comes back cold.

Durable memory is separate and opt-in. Record it only when a fact needs correcting, a lesson would otherwise be rediscovered, or an owner preference should persist. Bodies are committed markdown, so they never carry credentials or secrets — only that a secret exists, its scope, and where to fetch it.

Boundaries

Durable modes require an initialized database. Durable memory ships unwired from the spine playbooks by design — it is a store you reach for explicitly, not a default. And reduced modes, by design, leave no ledger: pick them for a bounded change, not for work that needs phases, waves, and a trace someone else will resume.
