Architecture

How the harness actually works, and why it is shaped this way. Decisions that are expensive to reverse have their own records under docs/decisions/; this page describes the running system.

The one idea

Committed markdown is the truth. Everything else is derived from it and can be thrown away.

That single constraint explains most of the design. The SQLite database is an index, not a store. The projected playbooks are a copy, not a source. The .kit/ directory is scratch, not state. If you deleted every derived artifact and re-ran the CLI, you would get the same system back, because the only irreplaceable bytes are the ones git is already tracking.

Markdown first, then the row

Every lifecycle write goes to markdown before it goes to the database, and the ordering is deliberate. A SQL transaction cannot span a file write, so the guarantee is one-directional by construction: a failed markdown write leaves zero rows behind it, while a database failure after a successful markdown write leaves the markdown line as the durable fact, recoverable by rebuild.

The consequence worth internalizing: a field that lands only in the database and never in markdown disappears on the next rebuild. That is the test any new mutating command has to pass.

harness.db is an index

The entire database is reconstructed from committed plan markdown alone. The file is gitignored, and losing it costs nothing. Three derived indexes share one column shape — path, SHA256, updated_at — and staleness is always a hash comparison, never a timestamp guess.

Managed docs: projection with conflict staging

The binary carries two embedded filesystems. The first holds AGENTS.md, WORKFLOW.md, and playbooks/; this set is projected into the consumer repo’s docs/ at init and hash-tracked. Templates are declared separately on purpose: they are never projected, only emitted when zharness scaffold asks for one.

On sync, unchanged files refresh silently. A file the consumer edited locally is not overwritten — it is staged as a conflict under .kit/conflicts/ and reported, unless --force-docs is passed. Removing a file from the embedded set leaves an inert orphan in already-initialized repos rather than breaking them; nothing in this package deletes.

Exactly one active plan

One resolver owns the active-plan invariant, and it never returns a bare error for the two interesting cases. Zero plans yields a stop whose recovery is brainstorm lock. Two or more yields a stop with a bounded candidate list built from frontmatter previews — plan bodies are never read to disambiguate. The enforced invariant is at most one active plan; zero is a legitimate idle state.

Preflight is the only entry point

Every spine stage begins with zharness preflight <stage> --json. It resolves readiness without mutating anything and returns the playbook path, the lifecycle position, and any drift. When the database or the projected docs are missing, preflight returns a stop whose recovery is zharness init. Skills do not self-scaffold; they run the recovery they are handed.

The four surfaces — skill, playbook, binary, plan — are the whole mechanism. Read them top to bottom and the system is one sentence: skills trigger, playbooks instruct, the binary guards, and markdown remembers.
