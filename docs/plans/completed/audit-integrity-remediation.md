# Plan: audit-integrity-remediation — recorded ownership, transactional recovery, one revision selector

## Outcome

- result: the eight findings of the 2026-09-07 integrity audit are closed at the
  source level, each by an exported-operation regression test rather than a
  helper test, so `zharness install/update/uninstall` and the pre-commit hook
  uphold the two README goals the audit falsified — *Safe to adopt and to leave*
  and *Invariants enforced, not assumed*.
- success_signals:
  - S1 [F01]: uninstall of an installer-created `AGENTS.md` that the consumer
    later appended prose to leaves the file on disk with that prose intact and
    the marked block gone.
  - S2 [F06]: `Install` run twice then `Uninstall` removes `docs/WORKFLOW.md`;
    no `.orig` record holding generated bytes survives the second install.
  - S3 [F07]: a `.gitignore` that already contained `/.zharness/` before install
    still contains it after uninstall.
  - S4 [F04]: an empty-but-existing file captured by `stashCapture` is restored
    as an empty existing file, not deleted.
  - S5 [F05]: `update --abort` with one stash payload removed returns a non-zero
    error naming the unrestored path and leaves `.zharness/update-stash/` on disk.
  - S6 [F02]: committing a plan under `docs/plans/completed/` whose final
    Validation entry cites a failing proof is rejected by the pre-commit guard.
  - S7 [F03]: a two-commit range whose first commit carries a failing proof and
    whose second is unrelated is rejected when guards run over the full range.
  - S8 [F08]: two nonempty staged active plans are rejected even when one
    worktree copy has been truncated without staging.
  - S9 [gates]: `cd cli && CGO_ENABLED=0 go build ./... && go vet ./... && go test ./...`,
    `bash scripts/test-guards.sh`, and `bash scripts/verify-doc-links.sh` all pass.

## Authority and Requirements

- authority:
  - `docs/audit/2026-09-07-integrity-review.md` — the findings, their evidence,
    and the remediation sequence (content first, verification second, ownership
    third, optional guarantees last).
  - `docs/decisions/0008-recorded-ownership-and-transactional-recovery.md` —
    authority for the ownership ledger, the `unknown` = keep rule, legacy
    seeding, the honest uninstall summary, and stash v2.
  - `docs/decisions/0009-guard-revision-selection-is-centralized.md` — authority
    for `zharness_guard_revspec`, completed-plan entry validation, and the
    advisory/gating split.
  - `README.md` — *Safe to adopt and to leave*, *Invariants enforced, not
    assumed*, *Diagnostics that name the next action*.
  - `scripts/install-git-hooks.sh` — the `ZGUARD-CORE` block is the
    authoritative guard implementation; `scripts/test-guards.sh` extracts it
    verbatim, so guard changes live inside the BEGIN/END markers.
- requirements:
  - R1 [accepted]: ownership of every managed path and every managed `.gitignore`
    line is recorded once in `.zharness/base/ownership.tsv` and never re-derived
    from filesystem state afterwards.
  - R2 [accepted]: `captureOriginal` runs only for a key whose recorded origin is
    `preexisting`, so generated bytes can never become their own pre-install
    original.
  - R3 [accepted]: uninstall removes only what the ledger attributes to the
    installer; `unknown` provenance is kept with a line naming why.
  - R4 [accepted]: an installer-created `AGENTS.md` is deleted only when the
    bytes outside the marked block are exactly the generated boilerplate;
    anything else is preserved with the block stripped.
  - R5 [accepted]: a pre-ledger installation is seeded from the `.orig` and base
    manifest evidence the old code already used, and only when a non-empty base
    manifest proves a prior install.
  - R6 [accepted]: the uninstall summary reports what was removed and what was
    kept; it never asserts a blanket preservation guarantee.
  - R7 [accepted]: the stash records an explicit `existed` bit; restore writes
    zero bytes when `existed=true` and removes only when `existed=false`.
  - R8 [accepted]: restore validates the whole inventory before writing anything,
    fails with an actionable error on any missing/unreadable/malformed entry, and
    keeps the stash directory until every entry has restored.
  - R9 [accepted]: a v1 (two-column) stash is read conservatively — a zero-byte
    blob is left alone rather than deleted — and the ambiguity is reported.
  - R10 [accepted]: `zharness_guard_revspec <event>` is the single source of the
    base/head under test; no guard call site computes `HEAD~1`.
  - R11 [accepted]: the pre-commit single-active-plan gate reads staged blobs,
    not the working tree.
  - R12 [accepted]: the Validation-entry guard selects both `docs/plans/active/`
    and `docs/plans/completed/`, with rename detection resolving an
    active→completed move to its destination.
  - R13 [accepted]: a push or PR whose base cannot be resolved fails closed with
    a message naming the missing history.
  - R14 [accepted]: `README.md` no longer cites a `validate` command; the binary
    surface described matches `install` / `update` / `uninstall`.
  - R15 [accepted]: L01 (judge is a self-declared string, not attestation) and
    L02 (unknown entry formats are ignored by design) are documented as stated
    limits.

## Non-goals

- NG1: no orchestration, database, or lifecycle state returns. The audit
  explicitly states these findings do not justify it.
- NG2: the bundle's `run.py` probe harness is not adopted. It compiles extracted
  functions in a standalone package and pins reviewed selectors; its scenarios
  become native Go tests and `test-guards.sh` fixtures instead. The audit itself
  warns against wiring its intentionally failing baseline into CI.
- NG3: no change to the deliberate fresh-overwrite policy for playbooks and
  `WORKFLOW.md` (ADR 0007). The audit agrees this is documented intent, not a bug.
- NG4: no schema validator for judge declarations or Validation entry grammar.
  L01/L02 are documented as limits this round, not closed.
- NG5: no release-checksum verification in `scripts/install-zharness.sh` and no
  macOS CI matrix. Both are real hardening; neither is data loss. Backlog.
- NG6: no new command, verb, or flag. Entity delta is one internal bookkeeping
  file and one stash column.

## Approach and Risks

- chosen approach:
  1. Land the two ADRs first, because Phase A and Phase C each change an
     externally observable policy and `AGENTS.md` requires named authority
     before such an edit.
  2. Phase A: an ownership ledger closes F01, F06, F07 and the false uninstall
     summary with one mechanism instead of three patches.
  3. Phase B: stash format v2 plus inventory validation closes F04 and F05.
  4. Phase C: one revision selector closes F02, F03, F08.
  5. Phase D: doc truth — land the audit report as cited authority, drop the
     `validate` claim, document L01/L02.
- rejected alternatives:
  - Alternative 1: eight independent patches, one per finding. Rejected because
    five of the eight are two root causes; patching the symptoms leaves the
    mechanism that generates them.
  - Alternative 2: treat missing provenance as installer ownership so uninstall
    stays tidy. Rejected on the asymmetry — a leftover file costs the consumer
    nothing they cannot delete; a wrong guess costs them work they cannot
    recover.
  - Alternative 3: keep the worktree glob for the plan count and add a staged
    check alongside it. Rejected because two sources of truth for one invariant
    is the defect, not the fix.
- risks and mitigations:
  - Risk (premise collapse): the audit could not build the repository — Go 1.23.2
    against a `go 1.25.0` module — so its probes prove the extracted *helpers*
    misbehave, not that the composed exported flow reaches those branches. All
    eight were re-confirmed by reading live source, but source reading is not
    execution. Mitigation: every fix lands with a test that calls the exported
    operation (`Install`/`RunUpdate`/`Uninstall`) or runs the real hook, so the
    end-to-end reachability is proven by the fix itself. This is why there is no
    investigation phase.
  - Risk: Phase C rejects commits that already landed on `master`. Mitigation:
    expected and named in ADR 0009 — reconcile the offending history
    deliberately; do not weaken the selector to make CI green.
  - Risk: legacy consumers lose tidy uninstall when `.zharness/base/` is gone.
    Mitigation: seeding recovers provenance wherever the old evidence survives;
    only genuinely unknowable cases degrade to keep-and-warn.
  - Risk: editing inside `ZGUARD-CORE` silently breaks extraction.
    Mitigation: `scripts/test-guards.sh` re-extracts the block and fails loudly;
    it is the verification for every Phase C task.

## Decisions
<!-- Append-only record of mid-flight decisions and trade-offs made during planning and execution. -->
- [2026-09-08 (planning)] (eight findings, three mechanisms): the audit's eight findings collapse into three root causes — ownership inferred from filesystem state (F01/F06/F07), stash restore as a loop rather than a transaction (F04/F05), and ad-hoc revision selection per guard call site (F02/F03/F08). Planned as three mechanisms plus a doc-truth phase rather than eight patches, so the generators of the defects are removed and not just their symptoms.
- [2026-09-08 (planning)] (exported-operation tests instead of an investigation phase): the audit's own stated limit is that it could not build the module and therefore exercised extracted helpers, not the composed flow.
