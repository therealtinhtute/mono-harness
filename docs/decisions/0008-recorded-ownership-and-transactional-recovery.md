# 0008 — Ownership is recorded, not inferred; stash restore is a transaction

## Status

Accepted. 2026-09-08. Authority for the externally observable behavior changes
in `docs/plans/active/audit-integrity-remediation.md` (F01, F04, F05, F06, F07).
Narrows the "consumer bytes are never destroyed" claim in
`cli/internal/installer/uninstall.go` from an assertion into an enforced rule.

## Context

The 2026-09-07 integrity audit (`docs/audit/2026-09-07-integrity-review.md`,
reviewed base `a456422`) reported eight findings. Five of them are two defects
wearing eight faces.

**Ownership is inferred from filesystem state.** The installer decides who owns
a byte by looking at what is on disk at the moment it asks:

- `captureOriginal` (`installer.go:259-277`) stats the destination. If the file
  is there, its bytes become the "pre-install original". On a second install the
  file is there because the first install put it there, so generated bytes get
  recorded as their own predecessor (F06).
- `removeAgentsBlock` (`uninstall.go:126-129`) reads the absence of an `.orig`
  record as proof of exclusive ownership and deletes the whole file, discarding
  any prose the consumer added after installation (F01).
- `Uninstall` (`uninstall.go:29-30`) passes the full managed-line list to
  `dropLines` with no record of which lines it actually appended, so a
  `/.zharness/` rule the consumer wrote themselves is stripped (F07).

Each is the same mistake: presence on disk is treated as evidence of provenance.
It is not. Provenance is a fact about the past, and the past is only knowable if
it was written down at the time.

**Restore is a loop, not a transaction.** `stashCapture` computes an `existed`
flag and throws it away — the TSV records only `path\tblob`, so an existing
empty file and an absent file both become a zero-byte blob, and restore reads
zero bytes as "remove this" (F04). `stashRestore` skips an unreadable payload
with `continue`, returns `nil`, and then `RemoveAll`s the stash directory, so
`update --abort` reports "pre-update state restored byte-for-byte" while a file
still holds its changed bytes and the only copy of the original is gone (F05).

Both defects sit directly under the README goal *Safe to adopt and to leave*.

## Decision

**1. A durable ownership ledger at `.zharness/base/ownership.tsv`.**

Rows are `kind<TAB>key<TAB>origin`, where `kind` is `file` or `gitignore`, `key`
is a repo-relative path or a literal ignore line, and `origin` is one of
`created_by_installer`, `preexisting`, or `unknown`.

An origin is written **once**, on the first decision for that key, and is never
revised afterwards. Later installs read the ledger instead of the filesystem.
`captureOriginal` runs only for a key whose recorded origin is `preexisting`, so
generated bytes can never be captured as an original.

**2. `unknown` means keep.** Uninstall deletes only what the ledger says the
installer created. A managed path with no recorded origin is kept with a
`KEPT` line naming why. Losing provenance costs the consumer a leftover file;
guessing costs them their work. The asymmetry decides it.

**3. Legacy installations are seeded, not guessed at.** An installation made
before this ADR has a base manifest and no ledger. On the next `install`, the
ledger is seeded from the same evidence the old code already relied on, and from
nothing else:

- a managed path with a captured `.orig` → `preexisting`;
- a managed path with no `.orig` → `created_by_installer`;
- a `.orig` whose bytes are exactly the recorded base blob for that path → the
  F06 artifact (a generated file recorded as its own predecessor) →
  `created_by_installer`;
- an ignore line present in the captured `.gitignore` original → `preexisting`;
  a managed line absent from it, or a `.gitignore` with no original at all →
  `created_by_installer`.

Seeding runs only when a prior install is proven by a non-empty base manifest.
A first-ever install into a brownfield repository decides live and records
`preexisting` correctly.

**4. The uninstall summary states what happened.** The unconditional line
`consumer-owned files were never touched` is replaced by a count of what was
removed and an explicit list of what was kept and why. A gate that reports a
blanket guarantee it does not enforce is worse than one that reports nothing.

**5. Stash format v2 carries existence, and restore is all-or-nothing.** The TSV
gains an `existed` column. Restore validates the entire inventory before writing
anything; a missing, unreadable, or malformed entry aborts with an error naming
the affected paths and **keeps the stash directory**. The stash is removed only
after every entry has been restored. A v1 stash (two columns) is read in a
conservative compatibility mode: a zero-byte blob is left alone rather than
deleted, and the ambiguity is reported.

## Consequences

- Uninstall after a lost or absent `.zharness/base/` now leaves managed files in
  place instead of removing them. That is a deliberate downgrade from tidy to
  safe.
- `update --abort` can now fail. A damaged stash returns a non-zero error and
  preserves the evidence instead of announcing a restoration that did not
  happen. Callers that assumed abort always succeeds must handle the error.
- An install performed by a pre-0008 binary and uninstalled by a post-0008 one
  behaves identically to today for every path where the `.orig` evidence is
  intact, because seeding reuses exactly that evidence.
- A v1 stash left behind by an interrupted pre-0008 update will not delete files
  on restore, but also cannot faithfully restore an absent one. It reports the
  ambiguity rather than resolving it in either direction.
- `ownership.tsv` lives under `.zharness/base/`, which `saveBase` does not clear
  (it clears `.zharness/base/upstream/` only), so the ledger survives every
  install and update.
- No new command, verb, or flag. The entity delta of this decision is one
  internal bookkeeping file and one stash column.
