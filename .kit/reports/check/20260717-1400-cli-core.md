## Findings

### Critical
- **SQL injection via unvalidated changeset field names (fixed this review)** — `cli/internal/infrastructure/changeset.go`: `applyCreate`, `applyUpdate`, and `applyMetaLine` built SQL by splicing changeset `fields` map **keys** directly into query text (`fmt.Sprintf("UPDATE %s SET %s ...", table, k+" = ?")` and the equivalent INSERT column-list construction), with no allowlist. `db changeset apply <path>` is a real CLI command that accepts *any file on disk* — a crafted `fields` key (e.g. `status='x'); ATTACH DATABASE ...; --`) would reach raw SQL identifier position unsanitized. Confirmed `Validate()` domain methods are never called anywhere (`grep -rn "\.Validate()"` → no matches), so no other layer catches this either.
  - **Fix applied**: added `entityColumns`/`metaColumns` allowlists (derived from `migrations.go`'s frozen CREATE TABLE column lists) and a `validateFieldNames` check invoked at the top of all three apply functions, rejecting any unknown field as `changeset_malformed` before it can reach query text. `last_applied_changeset`/`schema_version` are deliberately excluded from `metaColumns` too — those are `Migrate`/`setFence`-owned bookkeeping, not something a changeset line should ever set directly.
  - **Verification**: added `TestChangesetRejectsUnknownFields` (`cli/internal/infrastructure/changeset_test.go`) — exercises the exact injection-shaped key on both `create` and `update` paths, asserts the apply errors and neither creates nor mutates any row. Full suite re-run clean after the fix (`go test ./... -count=1` → 5/5 pass; `go build`/`go vet`/`CGO_ENABLED=0 go build` → pass).
  - outcome: fixed
