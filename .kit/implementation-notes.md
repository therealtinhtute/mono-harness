## 2026-07-17 12:35 cli-core/T3 — split `changeset_out_of_order` (ULID < fence) from the plain idempotent skip (ULID == fence)
**Decision**: `ApplyChangeset` treats a file whose ULID exactly equals the fence as a normal, silent no-op (`skipped_already_applied`, no error) — but a file whose ULID is strictly *less than* the fence additionally returns `changeset_out_of_order` (exit 1), even though the file is still safely skipped either way (no partial/duplicate mutation in either case).
**Spec gap**: SCHEMA.md's Idempotency Key Rules only state "ULID ≤ fence → skip, report `skipped_already_applied`" — worded as one uniform rule with no error. CONTRACT.md's error table separately lists `changeset_out_of_order (1, ULID predates the last-applied changeset — replay only, not a hard block, but flagged)` as a distinct condition. Neither doc states the `==` vs. `<` split explicitly; I inferred it by reading both together — SCHEMA.md's own later line ("an out-of-order manual replay is exactly the condition STATE.md's `out_of_order` stale-pointer rule detects and flags") only makes sense as a description of the `<` case, since a file re-applying its own exact fence value isn't "out of order," it's just already-applied.
**Tradeoff**: could have made both cases silently skip with no error (simpler, matches SCHEMA.md's literal wording alone) or made both cases hard-error (simpler, matches "flagged" alone) — chose the split because it's the only reading that satisfies both docs' wording without contradiction, and CONTRACT.md explicitly calls it "not a hard block" (the file is still skipped safely, not aborted).
**Risk**: low — this is a diagnostic-only distinction (both paths leave the db in the same safe state); if wrong, only the exit code/error code for one specific edge case changes, not any data mutation logic.

## 2026-07-17 13:05 cli-core/T4 — `import`'s idempotency is pre-check-based, not fence-based
**Decision**: before writing any changeset, `import` reads current DB state per entity (`storyByExactSlug`, `runByArtifactPath`, a `meta` column snapshot) and compares it against the intended value; only entities that are new or actually differ get a changeset written and applied. Unchanged entities are counted as `skipped` with zero `changesets_written`.
**Spec gap**: none — this is `import`'s own stated requirement ("one-shot idempotent: re-running produces zero new changesets"), which is strictly stronger than what the changeset engine's file-level fence alone provides, since `import` mints a *new* changeset file on every invocation rather than replaying an existing one.
**Tradeoff**: could have relied on the changeset engine's own idempotency (write unconditionally, let layer-1/layer-2 make redundant writes harmless) — rejected because that still produces a new `.changeset.jsonl` file on every run (violating "zero new changesets") even though it wouldn't corrupt data.
**Risk**: low — the pre-check reads happen outside any transaction relative to the subsequent write+apply, so a concurrent external mutation between the check and the write is a theoretical TOCTOU gap; not a concern for this CLI's single-user, single-process usage pattern.
